# P2.7: PR template sections that are not left empty

Status: built with this change. Written 2026-10-17. Friction row 48. Follows [P2.5](P2.5-ship.md) (`ship`, the PR body).

## What went wrong

PR #87 (P6 task 1, shipped by `ship --review-loop`) came out with `## Why` and `## What changed` empty and a very
long `## Summary`:

- **Why** is filled only from a line in the goal that starts with `Plan:` (`PRBodyBuilder.planTask`). The goal did
  not have one. Worse, when the describe step ran, `planTask` was called on the *model's summary*, not on the goal
  request, so a goal that did have the line would have lost it.
- **What changed** was filled by nothing. `fill` writes Summary, Why and Testing; any other template section keeps
  the template's own text, and HTML comments are dropped, so a section that is only a comment and an empty
  `<details>` ends up empty.
- The describe step returns `title`, `summary`, `decisions` and `deviations`. All of it goes under `## Summary`.

## What to build

1. **Why comes from the goal.** `planTask` reads `goal.request`. With no `Plan:` line and a described body, the first
   paragraph of the goal's request is used, since the model's text already sits in Summary. Without a description
   the section stays as the template has it (Summary is the request itself, so repeating it adds nothing).
2. **What changed is Workbench's, not the model's.** It is built from `git diff --numstat -M <base>...<head>`, as a
   per-file list inside the template's `<details>` block (`path`, `+added −deleted`; renames as `old → new`;
   binary files as `binary`), at most 40 rows and then "and N more files". It is words-free on purpose: a model
   cannot misstate it. Reading the diff failing never fails `ship`; the section keeps the template's text.
3. **The describe prompt asks for the right shape.** It tells the model the description is placed under the
   template's headings and that files, criteria and the check are added separately, and asks for `summary` in 2 to 4
   sentences (at most 1200 characters), a new `why` in 1 or 2 sentences (at most 400), and at most 3 decisions and 3
   deviations. The answer is held to the same limits: an over-long summary or why is refused like a bad title, and
   `ship` falls back to the goal's text. Why is the model's sentence followed by the plan reference when the goal has one.
4. **Goal drafts carry the plan line.** `goal new` puts a `(Plan: <path or task>)` hint comment in the Request so
   the omission is visible when filling the goal. (Left for a follow-up if the goal template is not in this repo's
   `goal new` yet.)

## Out of scope

- Having the model write a prose "what changed". The file list is deterministic; the prose stays in Summary.
- Changing the repository's PR template.
- Rewriting the body of PRs that are already open (`ship --refresh-description` does that on request).

## Tests

- `Plan:` line in the request fills Why, also when a description is given; the model's `why` comes first, then the plan.
- The describe answer: `why` is read and trimmed, refused when not a string or over 400 characters; a summary over
  1200 characters is refused; decisions and deviations are cut at 3.
- A described body with no `Plan:` line fills Why with the request's first paragraph.
- No description and no `Plan:` line leaves Why as the template has it.
- What changed lists files with counts, renames, binary files, caps at 40, and is omitted for an empty list.
- A template without a "What changed" heading is unchanged.
- `ship` against a repo: the opened PR's body has both sections filled (the existing `ShipOpenPRTests` fixtures).
