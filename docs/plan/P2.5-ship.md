# P2.5: Ship

**Outcome:** after you accept a thread, `workbench ship` pushes its branch and opens the pull request from the
goal, then reports CI. Claude is never given credentials and never pushes; Workbench does, as a separate,
recorded step you ask for. Still CLI.

**Depends on:** P2 accepted (accept exists and writes its decision).

## Scope

In:
- `workbench ship` for an **accepted** thread: push `workbench/<id>` to `origin`, open a PR against the
  goal's `base`.
- A PR title and description written from the work that was done: a read-only Claude turn is given the
  goal, the feedback sent back, the diff, the commits and the check result, and returns the title, a summary
  and the decisions and deviations to review. Workbench renders the body, so the criteria table and the check
  line always come from the real check. If that turn fails, the description is built from the goal alone. No
  paths from your machine appear in a description others will read.
- `workbench ship --watch`: read CI status for that PR until it ends or times out. Read-only.
- A `pr.opened` event, so the thread's log says what was shipped and where.

Out: merging (always you), fixing a red CI (that is send-back, a turn with the failure as the note),
posting review comments (`pr-review` skill), forks and multiple remotes, force-pushing anything.

## Design

### Why a separate step

P2 says accept means "this branch is good": it commits pending work and leaves a branch, with no push. That
stays true. Shipping is outward-facing and hard to undo, so it is its own command, run by you after
looking, with your own `git` and `gh` credentials. The run's environment is never involved.

```
workbench accept     branch is good, nothing left the machine
workbench ship       push + PR            (pr.opened)
workbench ship --watch                    CI result, read-only
```

### What it does, in order

1. **Preflight.** Thread is `accepted` and not yet shipped; worktree clean; `origin` exists; `gh auth
   status` is fine; the remote branch, if present, is an ancestor of ours (never needs a force); the base
   the pull request would target is on `origin` (otherwise `gh` would fail only after the push).
2. **Push** the branch with upstream set. Plain `git push`; a rejected push is reported, not retried
   with force.
3. **Create the PR** with `gh pr create --base <base> --head <branch>`. Title is the goal's title; body is
   built by a pure function from the goal and the check result, using `.github/pull_request_template.md`
   headings when the repository has one.
4. **Record** `pr.opened` `{url, number, branch, base, head_sha}`.

Idempotent: if a PR for the branch already exists, `ship` prints it and records nothing new.

### A thread that continues a branch

A goal with `push_to: <branch>` (made by `goal new --update <branch>`) is shipped to that branch instead of a
new one: step 2 pushes `workbench/<id>` to `refs/heads/<branch>`, still a plain push. Step 3 never creates
a pull request: it records the open PR for the branch and leaves its title and description alone, and refuses
when there is none. Preflight refuses, and nothing is pushed, when origin no longer has the branch, or when
the branch moved after the thread was cut (its tip is no longer an ancestor of ours): start a new thread from
its current tip. The rest, including worktree removal afterwards, works as for any thread.

**Keeping the pull request text true.** The branch's PR was written before this thread's work, so `ship` also
proposes edits to it. A read-only turn (no tools, its own session and budget, event `pr.refreshed`) is given the
PR's current title and sections, the goal, and what the thread added on top of the branch, and returns a new
title and new text for only the sections that work makes false or incomplete. Workbench applies that to the real
body: sections it names are replaced, every other line stays byte for byte (Windows line endings
included, which GitHub keeps for text typed in the browser), a block a bot wrote between `<!-- NAME -->` and
`<!-- /NAME -->` is never shown to the model and stays where it is, and a new heading in any Markdown form, an
unknown section, an empty text or a bot block in the model's text is refused. A section whose bot block is
inline or not at its end, or that holds a heading of its own, is not offered for editing and is left for a
person. `ship` prints each change as
removed and added lines and asks a second question, apart from "Publish this?". `--yes` alone never edits the
pull request; `--refresh-description` is the consent for scripts. Just before `gh pr edit` the PR is read
again, and if its text is no longer what the proposal was made from nothing is written. A failed turn, an
unusable answer or a failed edit never blocks shipping; the PR is recorded and the text is left for a person.
`--no-describe` skips the proposal.

### Same rules as the rest

Git and `gh` run through the bounded runner (`GitRunner`): `Spawner`, timeouts, capped output, no
inherited descriptors. Credentials come from the user's own environment, are never written to the log or
the argv shown in events. The PR text is written by a separate, read-only Claude turn (no tools, its own
session and budget, recorded as `pr.described`, never as a work turn) that sees only what Workbench
assembles for it. It supplies words only: the criteria table and the check line are rendered by Workbench
from the real check, and the result goes through the same path and credential scrub as the goal-based body.
`ship --no-describe`, or any failure of that turn, falls back to the body built from the goal.

## Tasks

1. **Preflight** (done: `Thread/Ship/ShipPreflight.swift`, `ThreadService.shipPreflight(id:gh:)`). Accepted and
   unshipped (no `pr.opened`), no live runner, worktree on `workbench/<id>` and clean, `origin` present
   (credentials removed from what is shown), `gh auth status` fine (only its exit status is used), and
   `origin`'s copy of the branch absent, equal or an ancestor. Reads only: `ls-remote` and
   `merge-base --is-ancestor`, no fetch, so a remote commit this repository lacks refuses as diverged.
   Returns a `ShipPlan` or throws a `ShipError`.
2. **Push** (done: `Thread/Ship/ShipPush.swift`, `ThreadService.shipPush(id:gh:timeout:)`). Runs the preflight, then
   `git push --set-upstream origin refs/heads/<branch>:refs/heads/<branch>` and nothing else: no force, no
   `+` refspec, hooks run as a plain push would. Own timeout (120 s), a rejection is `pushRejected` with the
   remote's message and credentials removed, and the push itself records nothing, so a rejected, timed-out or
   killed push is repeated by running it again. (Before the push, `ship` appends `branch.ahead` once per head
   when the branch is ahead of the accepted commit; running it again does not repeat that.)
3. **PR body builder** (done: `Thread/Ship/PRBodyBuilder.swift`). Pure function from goal and check outcome;
   honours the repository's template headings; tested without git. `Summary` is filled from the request,
   `Why`/`Context` from the goal's `(Plan: …)` line when it has one, `Testing` from the check line and the
   criteria; other headings keep the template's text and HTML comments are dropped, except `Screenshots`: it is left out when the latest verify step left no PNG, else holds `None` for `pr-shots` to take over. Without a template:
   Summary, Criteria, Check. Machine paths (`/Users/…`, `~/…`, `.workbench/…`) become `<path>`.
4. **Create PR and record** (done: `Thread/Ship/ShipOpenPR.swift`, `ThreadService.shipOpenPR(id:gh:timeout:)`).
   Needs the branch on `origin` at the tip. Looks for an open PR for the branch first (so a PR created but
   never recorded is recorded, not duplicated), else `gh pr create --base --head --title= --body-file`
   with `PRBodyBuilder`'s title and body and the template read from the base commit. Only a plain
   `https://…/pull/<n>` URL is accepted. Appends `pr.opened` last; once recorded, preflight refuses a
   second run as already shipped.
5. **`workbench ship` command** (done: `Sources/workbench/CommandsShip.swift`). `ship [id] [--yes]
   [--no-describe]`: without an id it takes the most recent accepted, unshipped thread; it shows the plan,
   runs the describing turn (`Thread/Ship/ShipDescribe.swift`, `PRDescriber.swift`; skipped by
   `--no-describe`, and a failure is printed and falls back to the goal-based body), prints the title and body it
   will publish, always asks `[y/N]` (no
   terminal and no `--yes` refuses), then push and PR, and prints the URL as its last line. Exit codes: 0 done,
   1 any other failure, 2 usage, 6 refused, 10 not accepted, 11 already shipped (URL printed), 12 push
   rejected or origin diverged (the table is `docs/spec/exit-codes.md`). Any failure is resumed by running it again. After the PR is recorded the worktree is removed
   when nothing could be lost (`--keep-worktree` opts out; `ShipCleanup`, event `worktree.removed`); the
   branch is kept.
5a. **`workbench clean`** (done: `Thread/Ship/ShipClean.swift`, `Sources/workbench/CommandsClean.swift`).
   `clean [--yes] [--closed]` asks `gh pr view <number> --json state,headRefOid` for each shipped thread and, for
   a merged PR (closed with `--closed`), removes the worktree `--keep-worktree` left and the local
   `workbench/<id>` branch. A dry run without `--yes`. Nothing goes unless GitHub's head, `pr.opened`'s
   `head_sha` and the local tip are one commit; an open PR, a failed lookup or newer local commits keep
   everything and say why. Never forced, never watches, never touches `origin`.
6. **`--watch`** (done: `Thread/Ship/ShipWatch.swift`, `ThreadService.watchPR`; `ship --watch`). Polls
   `gh pr checks <number> --json name,bucket` from the project root: prints each change once and the final
   list, ends at passed (0), failed (13) or no result in time (14, also when no check ever appears); bounded by
   `--timeout` (30 min default), a 30 s call limit and three failed polls in a row (exit 1). Writes nothing.
   After shipping it continues into watching; on an already shipped thread it only watches.

## Acceptance criteria

- [ ] `ship` refuses a thread that is not `accepted`, and nothing is pushed before accept.
- [ ] A shipped thread has a branch on `origin`, an open PR whose body lists the goal's criteria and the
      check result, and a `pr.opened` event with the URL.
- [ ] Running `ship` twice opens one PR.
- [ ] A rejected push leaves the thread accepted and unshipped, and says why; no force push exists in
      the code.
- [ ] No token or credential appears in `events.jsonl`, the argv recorded there, or the PR body.
- [ ] Killing the process during push or PR creation leaves a state `ship` can resume from, never a
      duplicate PR.
- [ ] `--watch` ends at a result or its timeout, and leaves no process behind.

## Risks

| Risk | Mitigation |
|---|---|
| A push of work you did not mean to publish | Only accepted threads; `ship` is a command you run, not a side effect of accept |
| Duplicate PRs after a crash between push and create | Look up an existing PR for the branch before creating; record after |
| PR body leaks local paths or logs | The describing turn has no tools and sees only an assembled input; its text and the goal's go through the same path and credential scrub, and the check output is never included |
| The model overstates what was verified | The criteria table and check line are rendered from the real check, not from the model's text |
| The describing turn fails or hangs | Own timeout and budget; any failure prints why and ships with the goal-based body |
| `gh` missing or not logged in | Preflight says so before anything is pushed |
| The goal's base exists only locally | Preflight refuses before anything is pushed and names the base to push or change |

## Demo

Accept a thread, run `workbench ship`, open the PR it printed, see the criteria and the check result in its
description, then `workbench ship --watch` until CI is green.
